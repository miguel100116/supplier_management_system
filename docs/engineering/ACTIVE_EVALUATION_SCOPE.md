# Uploaded Active Companies and evaluation assignments

Original approved rule, 2026-10-30: the latest admin-uploaded list for each category limits employee assignments. The Partner Registry is not an assignment list. Existing per-form company selections can narrow the uploaded scope; they cannot expand it. Registry additions do not create new assignments. No list, an empty list, or no valid registry matches yields no assignments. Read failures show an unavailable state, rather than a successful empty count or the entire registry.

Approved revision, 2026-11-10: a Master List upload records both the active-only history (`companies`) and complete non-archived category membership (`masterListCompanies`). The latest upload's membership remains the assignment boundary; current branch status determines eligibility. Inactive members remain visible in Manage Access with a disabled checkbox and an Admin-only Reactivate action. Reactivation sets inactive branches to Pending, clears a saved manual Inactive status, and the existing `partner_company` Realtime refresh recomputes assignment eligibility. Newly eligible companies start unchecked in the current picker; a previously saved explicit per-form selection is preserved and can resume after reactivation. Archived companies remain excluded and use the Partner Directory restore action.

Legacy snapshots contain only the active names and cannot safely reveal inactive membership. Migration `202611100001_master_list_company_membership.sql` adds the full-membership projection for new snapshots while preserving old history. After it is applied, an Admin must re-upload the current Master List once; until then the picker warns that its Companies Uploaded count reflects only the legacy active names. The migration has not been applied to staging or production.

Authorized extension, 2026-11-06: confirming a Master List import now generates all three current lists from the resulting registry in the same transaction. Recognized, unarchived companies qualify unless every branch is Inactive (including a manual Inactive status preserved under system-generated Completed); unset legacy statuses qualify. Merge includes retained existing partners; Replace uses only reviewed file records. Empty categories clear earlier scope and snapshot history remains. As of 2026-11-09, Directory > Register New Partner > Upload Master List has one combined CSV/Excel upload area; the separate category-list upload cards are removed. Select one consolidated Master List or multiple supported Master List files, with categories read from their rows. Existing dated snapshots and per-form company selections remain available; this does not add stored Master List source files or a new source-file history. Migration `202611060001_master_list_active_companies.sql` was applied to `supplier-management-staging` on 2026-11-09 following explicit owner authorization. The corrected RPC uses the existing private Admin/email helpers and runs as the caller with existing RLS and explicit confirmed-Admin checks. Function/ledger installation was atomic; before/after checksums for all 12 business tables, existing RLS policies and other functions matched. Live read-only database-role checks reject Employees/missing identities and reject malformed Admin input; no actual business-data import was performed. Production was not targeted. Failed database writes roll back both registry and snapshots. To roll back the code, restore the prior application and drop `public.import_partner_master_list(jsonb, text)`; preserve stored data and explicitly re-upload a prior selection if its restoration is required. Recovering partner records removed by Replace Registry requires a registry backup or source re-import; list snapshots alone do not restore partner documents. Disposable verification: `node scripts/verification/master-list-active-companies.rehearsal.mjs <path-to-installed-pglite/dist/index.js>`; this uses synthetic data only.

## Implementation

- `src/features/active-companies/domain/evaluationScope.ts` maps uploaded names to non-archived companies in the same category. It prefers a unique exact name, then the existing import normalization in `src/features/partner-companies/domain/companyName.ts`. No fuzzy matching, guessed classifications, or unrelated replacements are allowed. Unmatched and ambiguous names appear as a warning in the Admin company picker. Complete membership and current eligible IDs are derived separately; runtime fields never persist on surveys.
- `useSurveyData` reads the current membership during hydration and survey/snapshot reconciliation. It derives `activeEvaluationCompanyIds` and `uploadedEvaluationCompanyIds`; employee lists, forms, notifications, Dashboard targets and coverage use only current eligible IDs. Runtime scope fields are stripped from survey persistence and browser caches. Answers, registry records and saved per-form selections are preserved.
- `supabase/migrations/202610300001_active_evaluation_lists.sql` provides `get_active_evaluation_lists()`. Confirmed company accounts can read only category and company names from the latest saved snapshot. Upload history, filenames and uploader identities remain protected by existing Admin-only RLS. No RLS policy is widened. Anonymous and unconfirmed access is denied; the internal trigger function is not directly executable by authenticated users.
- Snapshot changes touch the matching survey rows' `updated_at` timestamps so the existing shared Realtime channel prompts employees to reload the projection. No survey payload is rewritten. Admin history and employee selection use the same timestamp ordering and deterministic ID tie-break. Deleted lists are not resurrected from bundled seed data.

## Rollout and recovery

The owner explicitly authorized staging application of the 2026-10-30 and 2026-11-06 migrations; they are installed in `supplier-management-staging`, matched to localhost's runtime URL. Production is untouched. Migration `202611100001_master_list_company_membership.sql` is authored locally but is not applied remotely. Once approved and applied, re-upload the current Master List to populate complete membership; the original workbooks are not retained for a safe backfill. Code compilation and synthetic tests do not prove live Realtime delivery.

1. Verify the target project and record the current schema/function/trigger inventory and list/survey payload checksums without logging confidential values. Follow the environment's backup procedure.
2. Apply the versioned migration, then verify anonymous denial, confirmed Employee access to the limited projection, private history remaining unreadable, and snapshot changes causing a signed-in employee refresh.
3. Promote the tested application. Check empty, failed-read and unresolved-name states as well as the configured active list. Do not repair business classifications or recreate partners automatically.
4. For rollback, revert the dependent application first, then drop `application_records_active_evaluation_list_change`, `notify_active_evaluation_list_change()` and `get_active_evaluation_lists()`. Keep all lists, registry entries, responses and survey payloads. Only survey invalidation timestamps are updated by the new trigger.

Read-only staging verification on 2026-10-30 matched localhost to `supplier-management-staging`. Its Supplier survey had no saved company subset and all 273 suppliers were unarchived; the uploaded Supplier list had 20 names. Existing normalization uniquely matched 19 of those names within Supplier. One listed supplier and one listed courier matched a registry entry in another category and require admin review; no classification was changed. All 13 listed subcontractors matched. Including existing per-form subsets, a read-only preview returned required company counts Courier 1, Supplier 19 and Subcontractor 13. These are dated observations, not hard-coded assignment counts.

After application, aggregate payload checksums matched for all 1,143 partners, 6,488 response rows, three forms and three upload snapshots; the RLS-policy checksum also matched. The projection and restricted invalidation trigger are installed with empty search paths. A read-only transaction using an existing confirmed Employee profile's claims under the actual `authenticated` database role returned the current category lists (7/20/13 names) while direct private-history reads returned zero rows. This verifies database-role/RLS behavior, not a real browser JWT transport. The live anonymous HTTP request returned 401. No business-data upload or response write was performed to test Realtime; live signed-in browser/Realtime verification remains unobserved because the computer-use browser/native hosts were unavailable.

The security advisor adds the expected notice for the intentionally authenticated `SECURITY DEFINER` read projection. Its exposure is limited to current category/company names, gated by the existing company-account helper, with anonymous execution revoked. The internal trigger remains non-executable by authenticated users. See [Supabase's advisory guidance](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable). Existing unrelated security/performance notices were recorded before rollout and were not changed.

Dashboard error handling now distinguishes record-loading failures from assignment setup/read failures. `useSurveyData` exposes the underlying data and assignment errors separately while retaining the combined error for employee task views. Admin Dashboard keeps loaded scores, document data, forms and recent submissions visible during an assignment error; assignment progress is unknown, never a successful zero. Other data-loading failures retain their existing unavailable states.
